# Java 1.8–26.3 compatibility and reliability audit

This fork starts from PrismarineJS/mineflayer commit `7b4bb8d2b56be9cdb832474af873acd37e609746`. The audit was performed on 2026-10-21/22 with Java Edition 26.3 as the current stable release. It includes source review, screening of 436 open issues and 118 open PRs, targeted regression fixes, companion dependency forks, and internal plus real vanilla-server testing. [UPSTREAM-TRIAGE.md](UPSTREAM-TRIAGE.md) preserves every screened issue/PR and distinguishes implementation from deferred or unverified reports.

The public Mineflayer API is retained apart from the additions and deliberate behavior changes listed under [Intentional API changes](#intentional-api-changes). This is not a claim that every upstream issue is fixed, every patch release has been exercised, or that third-party plugins or other proxies have been validated. Local Velocity proxy runs and online-mode runs against a stub session service are recorded separately from the runs with a real Microsoft account, signed in once by the account owner, against local online-mode vanilla servers (see VALIDATION.md). No upstream PRs were merged or issues closed by this work.

## Installation and reproducibility

Use Node.js 22 or newer and Git. From an application:

```sh
npm install github:HYPExMon5ter/mineflayer#audit/java-26.3
```

Pin a commit rather than the moving branch for deployment. Companion dependencies are pinned in `package.json` to commits, and minecraft-data to a built release archive because a Git install with scripts disabled does not include its generated data/submodule contents. Companion packages also pin the same data archive: root `overrides` alone do not propagate when Mineflayer is installed as a dependency.

The committed `npm-shrinkwrap.json` makes installs of this checkout (`npm ci`, CI) reproducible. It is deliberately not part of the package: the `files` allowlist excludes it (verified with `npm pack --dry-run`), so an application resolves Mineflayer's transitive dependencies through its own lockfile instead of being frozen to this graph, and keeps receiving their fixes. Packaging explicitly includes source, declarations, documentation and examples, excluding test worlds, downloaded server jars and local account data.

A Git commit pin is content-addressed; a GitHub release asset is not, because the fork owner can replace it. The tested minecraft-data archive `minecraft-data-3.117.0.tgz` of release `java-26.3-data-9` has SHA-256 `423dc8f137d661baffe35fc86db231e6ad3858583665a7d643d8326c3ac98ce5` (npm integrity `sha512-cyO+6YLkQbxL58jBSTVD5GuNnMxzpDqmXQEl8sAEg6PjG9w1G9WDnSdp1fdV9sc3aGF/FmbVFoSgWs7K040wUw==`, recorded in the shrinkwrap). The asset downloaded on 2026-10-23 matched both, and is byte-identical to the archive built locally and tested before publishing. Earlier releases (`data-2` to `data-8`) remain published but are superseded. An application's lockfile records the integrity of the archive it first installed and rejects a later replacement; verify the hash before that first install if it matters.

## Significant findings and changes

### Wire compatibility

- Upstream had started writing string action names to legacy numeric `entity_action` and `client_command` fields. On 1.8 this made waking encode as sneaking; statistics requests could encode as respawn and stall creative-slot confirmation. `lib/protocolActions.js` selects numeric values or mapper names/aliases from the actual schema. Tests serialize the real packets for all 30 versions.
- Added 26.2/26.3 data, protocol, chunk and physics support through the companion chain. Corrected unsigned lpVec3 scaling and rejected malformed empty entity-delta paths. Entity velocities already expressed in blocks/tick are no longer divided by 8000.
- Corrected 26.3 sign packet field order and front/back slot encoding against the vanilla server classes. The sign suite exercises server-echoed text, not merely successful packet serialization.
- Compared the data with what servers report and send (see [Second follow-up](#second-follow-up)): the 26.3 serverbound table (`0x3f` is `spectator_action`; there is no swing packet), 26.3 sounds/particles/tool IDs, attribute IDs (1.21.1–26.3), command argument types, tool materials (1.20.5–26.3), 1.20.5 enchantability, 1.8–1.12 block hardness and names, 1.20.3 vibration particles, every tool's dig speed on every block (1.17–26.3, see [Third follow-up](#third-follow-up)), and `declare_recipes`, `set_player_inventory`, `explosion` and `teams` packets that real servers sent but the data could not decode. The vanilla suites now fail on any packet that is not decoded completely.
- Adapted 26.3 digging/release action IDs, movement deltas, entity animation IDs, per-axis particle speeds, and widened teleport confirmations. Strict 26.3 movement scheduling emits at most one movement packet per client tick, including queued teleports and respawns.
- Fixed modern mock-server login success packets to include a session UUID. Custom protocol overrides no longer mutate shared minecraft-data or leak between override objects. Protocols built from one `customPackets` object are cached for that object, so clients and state changes sharing it compile once; compiled and interpreted paths have isolation and reuse tests.

### State and lifecycle

- Plugin injection happens before packets can arrive. Entity-placement waits survive unrelated spawns. Bed, book and promise timeout paths clean up listeners/timers and restore state.
- Resource-pack responses use the correct ID/hash shape and acknowledgement sequence, answer each request once, and can address one of several outstanding 1.20.3+ packs. During configuration a request that no listener answers synchronously is accepted, as upstream does, so logging listeners cannot stall a transfer; this does not download or apply resource-pack assets.
- Inventory state IDs are tracked per window. Closing, respawning and re-login have explicit lifecycle handling. Unknown window types emit `unknownWindow` instead of dereferencing a missing window. Creative-slot updates compare nullable items and release locks on every exit.
- Item-use state survives unrelated entity status notifications and understands modern cooldown groups. Passenger/vehicle links are reconciled before attach/detach/mount events, including vehicle removal.
- Health distinguishes metadata bitmasks from legacy booleans; dimension transitions emit spawn without inventing a death. On 1.21.4+ `player_loaded` waits for terrain or a bounded fallback, and on every version `spawn` (with `player_loaded`) waits for the confirmation of a teleport the bot has not answered yet; both are cancelled when the session changes. World chunk ownership includes world name, not just dimension type.
- Modern score/reset packets, chat-component objective titles, cleared display slots, empty titles and overlapping chat patterns are handled. Plain-string titles, including legacy `§` formatting codes, are kept as sent. Time resolves world clocks through the registry and preserves overworld day time across dimensions.

### Correctness and test efficiency

- Cursor raycasts accept zero yaw/pitch and start at eye height. Look promises wait for both axes. Dig duration is calculated after aiming. Anvil limits use version features. Explosion exposure uses entity dimensions and handles zero-size/zero-distance samples. Empty chunk batches cannot poison the pacing average.
- Exact `MC_VERSION` selection happens before loading registries. Unit tests run independently from server suites. CI caches dependencies and server jars, retains bounded version groups, and has a stable aggregate gate; failed processes are detected by exit status, including failures before Mocha prints a summary.
- Trace-worker errors cannot make shutdown wait forever. Trace tests clean their temporary files. The cooldown test removes its thrown pearl before the next test: leaving it airborne could teleport the bot out of the Nether later. Nether tests acknowledge arrival before a second teleport and bound terrain waits with diagnostics. Empty-server pausing is disabled in the harness so modern status/login probes remain responsive. Internal teardown lets the bot's connection attempt settle before closing the server, the vanilla world reset also treats chunk resends as changes, and the Nether test accepts the arrival teleport before or after `spawn`. The villager fixture uses a stable demand-driven price rather than a reputation discount the server can reset; discounted (negative `specialPrice`) pricing is covered by a unit test of vanilla's cost formula instead.
- These are concrete reductions in redundant setup, blocked work and failure diagnosis. No general runtime throughput/CPU improvement percentage is claimed; this audit did not run a controlled application benchmark.

## Intentional API changes

- `scoreboardPositionCleared` (position, previous) is new: it reports a display slot that stopped showing an objective. `scoreboardPosition` keeps a non-null scoreboard and documents its existing third `previous` argument.
- `bot.acceptResourcePack([request])` and `bot.denyResourcePack([request])` take an optional request id (UUID or hash) or URL. Without one they answer the most recent request, as before. The `resourcePack` declaration now names its second argument `hashOrUuid`, which is what has always been passed; the never-provided third parameter remains only for source compatibility.
- During configuration a resource pack that no listener answers synchronously is accepted after the event. Upstream accepted unconditionally, even after a listener declined; an earlier revision of this fork let any listener suppress acceptance, which stalled transfers for listeners that only logged.
- `unknownWindow` also closes the unsupported menu on the server.
- On 26.3, `entitySwingArm` comes from the swing animation packet and covers main-hand swings, like older versions.
- On 26.3, `bot.swingArm('right')` sends the main-hand attack swing (`punch`), which also resets the attack cooldown as in vanilla; `swingArm('left')` sends nothing because 26.3 has no packet for it, and placement and `activateBlock` no longer add a swing the server already performs. Other versions are unchanged.
- `anvil.combine` and `anvil.rename` move the exact items passed and resolve after taking the result the server produced for both items and the final name. Before, they could pick another item of the same type, and on 1.17+ could leave the result on the cursor or take an earlier result. `anvil.combine` without a name keeps the custom name of the item the result is based on, as the vanilla client does; before, it sent an empty name, which removed the name and cost a level.
- `placeEntity` places boats, chest boats and rafts on every version; from 1.21.2 the resolved entity is of the item's own type (for example `oak_boat`).
- On 1.14–1.18 the world adopts the block that the server's digging acknowledgement reports when the server refused the action or a finished dig left the block in place, as the vanilla client does; before, a refused break stayed predicted as air.
- Gravity set to `0` by `bot.creative.startFlying()` is restored when the server removes the ability to fly, e.g. on leaving creative mode.
- With the prismarine-item fork, `item.enchants` on 1.20.5+ is `{ name, lvl }[]` (books: their stored enchantments) instead of the raw component, and setting it, `repairCost`, `customName` or `customLore` changes what `Item.toNotch` sends. The name and lore setters store the NBT component the server writes (a style-free text as a string tag), so reading them back gives that component's JSON, e.g. `"Cool Sword"` for `{"text":"Cool Sword"}`; `null` removes them.
- minecraft-protocol sends each chat message and command with a timestamp no earlier than the previous one on that connection, also when the system clock steps back; a timestamp passed by the caller is sent as given.
- With a chat session (signed in with Microsoft, 1.19.3+), minecraft-protocol holds chat messages and commands written before the server has applied the session and sends them, in order, once it has: on joining it sends a statistics request after the session update and waits for the answer. The new `client.requestStatistics()` resolves with the `statistics` packet that answers a request; `bot.creative.setInventorySlot` uses it, so answers are matched to requests across the connection.
- With data-9, 1.17–26.3 blocks whose tools differed from the rest of their material have new material names (`plant;mineable/hoe`, `sword_instantly_mines`, `sword_instantly_mines;mineable/axe`, and `mineable/hoe` for the 26.3 straw bed), and several materials' tool multipliers changed (see [Third follow-up](#third-follow-up)).
- Data names that consumers can see changed with the data fixes: 26.2/26.3 command parsers `minecraft:team_color` (was `color`) and the five 26.3 parsers, newly listed attribute names, and 26.3 sound and particle names now at their vanilla IDs. On 1.11/1.12 the blocks `light_gray_shulker_box` and (1.12) `light_gray_glazed_terracotta` are named `silver_shulker_box` and `silver_glazed_terracotta`, as in vanilla and in the items of the same versions. `end_gateway` and `structure_block` on 1.9–1.10 and the repeating and chain command blocks on 1.9–1.11 are no longer `diggable`: vanilla makes them unbreakable.
- On 1.21.2+, the bot's own teleports apply the packet velocity and its relative flags, rotate the velocity for `yawDelta`, and clamp pitch to ±90°, as vanilla does. Previously an absolute teleport always zeroed the velocity.
- On 1.21+, physics applies the soul sand/honey speed factor and climbable trapdoors above ladders, which vanilla still implements.
- `bot.writeBook` rejects with an `AggregateError` of the original and the restore error when moving the book back also fails.
- `bot.isAlive` and `bot.time.clocks` existed but were undocumented; they are now documented and typed.
- On 1.21.4+, `spawn` is emitted right after `player_loaded` is sent: once the chunk at the player's position has arrived (at once outside the build height or in spectator mode), or after the server's 3 second timeout. Upstream sent `player_loaded` and emitted `spawn` on the health update. A death while loading emits `death` and no `spawn`; a new login, respawn or disconnect cancels a pending spawn. On every version `spawn` also waits until the bot has confirmed the server's latest teleport, which it answers on the next tick (on 1.8 after a death up to 1.5 s later), so `forcedMove` for the spawn teleport usually comes before `spawn`; upstream emitted `spawn` first.

## Review follow-up

An independent review of the first published revision (`216b3abd`) raised the findings below. Each was reproduced or checked against vanilla 26.3 server bytecode before changing behavior, and each change has a test that fails without it unless noted.

| Finding | Disposition |
|---|---|
| 26.3 arm swings use `swing_animation`, so `entitySwingArm` never fired | Fixed. Packet layout confirmed from `ClientboundSwingAnimationPacket`; the animation table is chosen once per bot from the schema. Unit and wire-level internal tests. |
| `dig(bedrock)` aborted the active dig and turned the bot first | Fixed. Dig time is validated before aiming and again after aiming, before the active dig is stopped; the `is Infinity` message is kept. |
| `scoreboardPosition` emitted an undefined scoreboard on clear, contrary to its types | Fixed with the separate `scoreboardPositionCleared` event; types and consumer test updated. |
| Legacy (1.8–1.12) scoreboard titles lost `§` codes | Fixed. Only genuine JSON components are converted; plain strings are kept, and JSON titles still read as text on every version, as upstream did. |
| Logging-only `resourcePack` listeners stalled configuration; wrong declaration; only the latest pack answerable | Fixed as described above. Per-request answers are an optional argument rather than a new API shape. |
| `customPackets` disabled the compiled-protocol cache (~100 ms per state per client) | Fixed in minecraft-protocol `fccbf55` with a cache keyed by the `customPackets` object; repeated state changes reuse it. Local timing: ~85 ms for the first compile, ~0.05 ms for reuse, a single observation rather than a benchmark. |
| `unknownWindow` left the menu open on the server, so later clicks time out | Confirmed: vanilla `handleContainerClick` ignores clicks for any container other than the open one. Fixed by closing it. |
| Creative `Item.equal` could reject an equivalent server echo | Confirmed with a different cause: on 1.21.3+ `Item.toNotch` drops NBT-only properties, so an echo of exactly what was sent differed from the caller's item. Echoes are compared with the item as sent. NBT key order itself is not compared on these versions. |
| `nbt.addTypesToInterpreter` may not exist in prismarine-nbt `^2.5.0` | Not a defect: 2.5.0, 2.6.0 and 2.7.0 all export `addTypesToInterpreter`; only the 2.5.0 changelog entry misspells it. The range is correct. |
| Proxy re-login without respawn never emitted `spawn` or `player_loaded` | Fixed: every login marks spawn pending; the initial spawn is emitted once. |
| Own-player 1.21.2+ teleports ignored velocity values and flags | Fixed with the vanilla `PositionMoveRotation.calculateAbsolute` rules shared with entity teleports. Internal fixtures that omitted the velocity fields (sent as NaN) were corrected. |
| Chat pattern loop crashed if a listener removed a later pattern | Fixed and tested, including deprecated patterns. |
| Physics feature lists stopped at 1.20 for `velocityBlocksOnTop` and `climbableTrapdoor` | Fixed in prismarine-physics `31b5117`: features are inclusive version ranges, checked against vanilla 26.3 (`getBlockSpeedFactor`, `trapdoorUsableAsLadder`). Only these two features changed for any version. |
| Passenger moving A→B with B's packet first never reported leaving A | Fixed: `dismount`/`entityDetach` for A precede the attach to B. |
| `bot.time.clocks` and `bot.isAlive` undocumented | Documented and typed. |
| Per-packet version comparison in the animation handler | Removed. `strictMovementTicks` remains a single inject-time 26.3 check because no data feature describes it and adding one would need a data fork change. |
| Action enum resolution repeated per packet | Cached per registry. |
| Entity relative teleports did not clamp pitch | Fixed with the shared resolver. |
| Book restore failure hid the original error | Fixed with `AggregateError`. |
| Internal logs could not be told apart; identical hashes across versions | Confirmed: the dot reporter never printed the version. New logs use the spec reporter and start with the version and exact revisions. Old logs were not relabelled. |
| Passing internal tests printed ECONNABORTED/ECONNREFUSED | Caused by tearing a test down while the bot was still connecting. Teardown now lets the connection attempt settle and disconnects the bot before the server; no error output is suppressed. |
| Negative trade-price coverage was lost | Restored as unit coverage of vanilla's cost formula, which also now uses float arithmetic like vanilla. |
| `npm-shrinkwrap.json` is not packed | Confirmed and kept: see Installation. The documentation no longer implies consumers receive it. |
| GitHub release asset is replaceable | Documented with its SHA-256 and npm integrity. |
| Found while validating: two vanilla-harness races | The world reset skipped its refill when a test changed the world only through whole-chunk resends (fishing's water fill), so the next test built on water; column loads now mark the world dirty. The Nether test waited for the arrival teleport only after `spawn`, although the server sends it first; it now waits for both after the dimension change. Both were reproduced with event traces before the fix. |

## Second follow-up

The remaining validation gaps of the first follow-up were worked through: the protocol round-trip suite, the excluded vanilla tests, live proxy and authentication checks, and a vanilla-report comparison of the data. Each defect below was reproduced before it was changed, against vanilla server bytecode, a server's own registry report (`--reports`) or a real server, and has a test that fails without the fix unless noted.

| Finding | Disposition |
|---|---|
| 26.3 serverbound `0x3f` was `arm_animation`; vanilla registers `spectator_action` there and has no swing packet | Fixed in the data (`6753283`). `swingArm` writes `arm_animation` where it exists; on 26.3 it sends `punch` for the main hand (as the vanilla client does when attacking or mining) and nothing for the off hand, and placement/`activateBlock` no longer send a swing, which the 26.3 server performs itself. Before, `swingArm('left')` asked a spectating bot to spectate entity 0. Every packet table of 26.1–26.3 was compared with the server's registration order. |
| 26.3 packet round trip: 71 failures | The generator now derives values for named types from the schema, gives mappers real names and skips void anonymous branches; it no longer hard-codes component IDs that later versions lack. ## Signed chat on joining

Before publication, the real Microsoft account check was repeated at `7b3a5ae8` (the dependencies of `912e8ca2`) and failed: the bot spawned, but the 26.3 server dropped its chat with "Failed to update secure chat state: Chat disabled due to missing profile public key", although the client had fetched its keys (HTTP 200) and announced a chat session.

| Finding | Disposition |
|---|---|
| Chat sent soon after joining reached the server before it had applied the chat session, so the server took the signed chat as unsigned and secure chat rejected it | Traced with packet names and times: the client sent `chat_session_update` on the login packet and its chat on spawn about 80 ms later; the rejection came 2 ms before the server echoed the session as applied. From 1.21.9 the server hands the session update to a packet queue drained once per tick but handles chat from its main task queue, which also runs between ticks (`PacketUtils` and `ServerGamePacketListenerImpl` in the 1.21.9, 1.21.11 and 26.1–26.3 jars); 1.20.6–1.21.8 handle both from the main task queue in arrival order. Without the fix the chat was rejected on every run on 1.21.11 and 26.1–26.3, and passed on 1.19.3, 1.20.4, 1.21.8 and, in three runs, 1.21.9. Fixed in minecraft-protocol (`e4e60be`, comment corrected in `005d953`): after the session update the client sends a statistics request, which the server answers from the same queue after applying the session, and holds chat and commands until the answer, then sends them in order. A server slowed to 2 ticks per second and chat sent on the login packet itself (which fails on 26.3 without the fix) both pass. Unit tests on 1.19.3–26.3 check that chat is held, sent in order and signed, and that clients without a session are unaffected; the holding tests fail without the fix. Fixed and unfixed live runs are listed in VALIDATION.md. |
| Mineflayer's creative slot confirmation matched statistics answers to its own requests | The protocol's request at joining would have been taken as the answer to the first creative request, and every later confirmation would have resolved one answer early. Creative now uses `client.requestStatistics()`, which matches answers to all requests on the connection in order (`ec5885d6`); a request that times out keeps its place, where before its late answer resolved the next request. |

## Remaining limitations

- `npx tsc --noEmit` over the complete declaration graph fails in existing prismarine-chat, prismarine-nbt, prismarine-windows and protodef declarations (and a chunk interop setting). `test:types` compiles a real consumer of the changed APIs with `skipLibCheck`; it validates consumer usage but does not certify dependency declarations.
- The dependency audit reports known transitive advisories, including uuid under the authentication chain and older development tooling. Suggested automatic fixes include downgrades and unrelated API changes. They were not blindly applied; at the evidence commit the development graph has 18 findings (9 high, 8 moderate, 1 low), as at the second follow-up. This is not a clean security audit.
- Minecraft resources and server caches are local test inputs, not redistributed in the package. No Microsoft account credentials or existing user server settings were changed.
- Anti-cheat/proxy-specific behavior beyond the local Velocity runs, relighting, additional GUI plugins, major movement/digging rewrites and unverified feature requests remain explicitly deferred in the triage. A passing vanilla suite does not prove those environments.
- Real Microsoft/Mojang authentication used one account, signed in once by its owner and then from its cached session, against local vanilla servers of 1.19.3, 1.20.4, 1.21.4, 1.21.8, 1.21.9, 1.21.11 and 26.1–26.3 (see VALIDATION.md). Proxies in online mode with a real account, token refresh, and servers that do not answer statistics requests were not tested; on such a server chat from a Microsoft-signed bot would stay held.
- prismarine-physics looks the movement speed attribute up by its registry resource name (`minecraft:movement_speed`), but 1.20.5+ attribute packets name attributes as minecraft-data does (`generic.movement_speed`), so server attribute modifiers to movement speed are not applied; speed effects are handled separately. This predates the audit and is unchanged.
- minecraft-data for 1.14.4/1.15.2 lacks the crossbow enchantments (it reuses the 1.13.2 list); not changed.
- Container operations (`withdraw`, `deposit`, the furnace's `take*`, `clickWindow`) resolve on the client's prediction, as upstream. From 1.21.9 the server handles window clicks from its per-tick packet queue but commands at once, so a command sent right after such an operation can run before its clicks. Rechecked at `970eba23` on 26.3: a `/clear` sent right after withdrawing three stacks from a chest and closing it removed nothing, the server still held all three stacks afterwards, as `bot.inventory` did, and a later `/clear` removed them and updated the client; 1.21.8 removed them at once. The vanilla suite's resets show the same order after the furnace test (the first `/clear` removes 4 items on 1.21.8, 1 on 1.21.9+). The earlier record, from the second follow-up, that the server then never sent the emptied slots so the client kept the items, is not supported by this check, which found the client right in every round; that earlier observation was not reproduced, so its mechanism is not established. Code that depends on the server's inventory should wait for the slot updates it expects.
- `bot.dig` resolves when the bot has sent the finish packet and predicted the block as broken, as before; it does not wait for the server. From 1.21.9 (whose server jars hand game packets to a queue drained once per tick; checked in the 1.20.6–26.3 jars) a command sent right after `await bot.dig()` can run before the server applies the break. Code that depends on the server's state should wait for the block update at that position. Behavior is unchanged from upstream.
- From 1.19 Mineflayer does not roll back a predicted block change the server did not confirm, which the vanilla client does on the digging acknowledgement. A finish the server finds too early is delayed, not refused, so the bot sees the block broken a few ticks before the server breaks it. `digEverything` asks the server after each dig, so it catches a delay still pending when the server has handled the dig, not one of a few ticks. Unchanged from upstream.
- Runs of the vanilla suites on all 30 versions on this machine have often shown one failure in a different test each time; VALIDATION.md lists every failed attempt of this round. The earlier `exampleDigger` failure on 1.21.3 was not reproduced and its cause is not established.
- `digEverything` fails a dig the server applies a few ticks after the bot finished, which is how the data errors showed up, so a server that falls behind (a garbage collection pause, many servers running at once) can fail it for a correct dig; this happened once on 1.17.1 with seven servers in parallel.
- Tool speeds were compared with vanilla only where the server decides them by tags: every tool from 1.17, swords from 1.20. Before 1.17 (and swords before 1.20) vanilla decides by block material in code, which was not compared beyond the cases `toolSpeeds` digs; for example a sword breaks bamboo at once from 1.14, which the data gives only from 1.20. Blocks behind an experimental flag were not compared.
- The upstream PRs that overlap the prismarine-item fork (#176, #186, #190) are unmerged and were not merged into it; the fork contains an independent, smaller change.
